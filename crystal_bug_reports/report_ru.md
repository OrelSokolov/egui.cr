# Баг-репорт — crystal-lang/crystal (русская версия)

Заголовок: **Proc(*T, R), приведённая к Proc(*T, Nil): место вызова не
совпадает с конвенцией возврата замыкания — утечка слотов x87 (тихий
NaN) или сдвиг аргументов (SIGSEGV)**

(Перевод `report_en.md`; в issue на GitHub лучше отправлять английскую
версию — эта для внутренней документации.)

## Окружение

- Crystal 1.21.0 [57cf7da50] (2026-07-16), LLVM 20.1.8, самосборка
- Crystal 1.22.3 [3462c0774] (2026-11-13), LLVM 22.1.3, официальный
  дистрибутив
- Цель по умолчанию: x86_64-unknown-linux-gnu (Debian, glibc 2.4x)
- Воспроизводится и в dev, и в `--release`

## Суть

Замыкание, тело которого возвращает структуру, можно сохранить в
`Proc(*T, Nil)` (неявная ковариантность возврата к `Nil`). Функция
замыкания компилируется со своим **настоящим** типом возврата, а место
`.call` — так, будто прок ничего не возвращает. Для
структур из нескольких полей эти конвенции не совпадают:

1. **Полностью числовая структура (например, 4 × Float64): части
   возврата едут через стек x87.** Эпилог вызываемого пушит st(0)/
   st(1) (`fldl`), а вызывавший, не ждущий возвращаемого значения,
   их никогда не выталкивает (`fxch`/`fstp` отсутствуют). Каждый
   вызов течёт на 1–2 слота x87; стек x87 всего 8 слотов, поэтому
   после нескольких вызовов любой следующий возврат структуры
   переполняет его и читает обратно **QNaN indefinite
   (0xFFF8000000000000)** — тихая порча не связанных, совершенно
   конечных значений.

2. **Структура, возвращаемая через скрытый sret-указатель (например,
   с целочисленными полями): вызывавший не передаёт буфер возврата**,
   и вызываемый читает все аргументы со сдвигом на один регистр —
   неверные значения или SIGSEGV.

Найдено «в бою» как «фантомные NaN» в геометрии GUI-фреймворка: цикл
`CASES.each { … render.call(ui, i) }` по прокам типа
`Proc(Ui, Int32, Nil)`, чьи тела неявно возвращали `Rect` из
4 × Float64, умирал на 5-й строке с `Rect#width: non-finite value NaN`
при конечных входных данных.

## Влияние — почему это тяжело отлаживать

Порча **тихая и далеко от своей причины**. Утечка x87-слотов
происходит в одной функции, а итоговый QNaN indefinite всплывает в
*совершенно постороннем коде*: любая следующая функция, возвращающая
структуру из нескольких float-полей, получает `NaN` в части полей — при
достроенно конечных аргументах (`Rect.new(10.0, 20.0, 30.0, 40.0)` →
`NaN, NaN`). Для пострадавшего это выглядит ровно как **ошибка в
математике той функции, которая вернула NaN**: печатаешь её входы
(конечные), проходишь под отладчиком (конечные), а она всё равно
возвращает NaN — потому что FPU-стек переполнился несколькими вызовами
раньше в не связанном замыкании. Мы потеряли на это дни; локализовать
удалось только гвардами в «местах рождения NaN» (проверки `finite?` в
конструкторах структур), а настоящую причину — лишь полной сессией в
gdb на уровне инструкций (учёт fstpl/fldl и tag word x87).

## Предлагаемый фикс

`proposed_fix_from_GLM.patch` (в этой же папке; авторство — модель
GLM / агент H2Code, отсюда и название): запрет void-каст ковариантности
в `ProcInstanceType#compatible_with?` и в Nil-ветке `restrict(other :
Generic)`, когда исходный тип возврата — struct-подобный. Тихая порча
превращается в понятную ошибку компиляции (`expected argument … to be
Proc(…, Nil), not Proc(…, Quad)`), все безопасные возвраты через
регистры (примитивы, enum'ы, объединения, указатели, проки, ссылки)
продолжают работать. Проверено: бутстрап компилятора,
`spec/compiler/semantic/proc_spec.cr` (194 примера), оба варианта
репро теперь падают компиляцией вместо порчи памяти. Правильное
долгосрочное решение — синтез обёртки в точке коэрции; патч —
консервативная временная мера.

## Воспроизведение

Файл: `crystal_bug_repro.cr` (в этой же папке; вариант 2 — с
`REPRO_SRET=1`). Детерминированное, только stdlib.

```crystal
struct Quad
  property a : Float64
  property b : Float64
  property c : Float64
  property d : Float64

  def initialize(@a = 0.0, @b = 0.0, @c = 0.0, @d = 0.0)
  end
end

# Структура должна пересекать границу настоящего вызова, чтобы конвенция
# возврата имела значение; @[NoInline] не даёт это соптимизировать.
@[NoInline]
def make_quad(a : Float64, b : Float64, c : Float64, d : Float64) : Quad
  Quad.new(a, b, c, d)
end

procs = [] of Proc(Int32, Nil)
8.times do
  procs << ->(x : Int32) {
    make_quad(x.to_f64 + 1.0, x.to_f64 + 2.0, x.to_f64 + 3.0, x.to_f64 + 4.0)
  }
end
procs.each_with_index { |proc, i| proc.call(i) }

check = make_quad(10.0, 20.0, 30.0, 40.0)
if check.a.nan? || check.b.nan? || check.c.nan? || check.d.nan?
  puts "BUG: phantom NaN => #{check}"
else
  puts "OK: #{check}"
end
```

Вывод (`crystal run`):

```
BUG: phantom NaN => Quad(@a=10.0, @b=20.0, @c=NaN, @d=NaN)
```

`--release` (один утёкший слот на вызов вместо двух):

```
BUG: phantom NaN => Quad(@a=10.0, @b=20.0, @c=30.0, @d=NaN)
```

## Анализ (дизассемблер x86-64, вариант 1, dev-сборка)

Замыкание сохраняет настоящую сигнатуру — это `~procProc(Int32,
Quad)` — и возвращает Quad как две XMM-части плюс **два пуша в x87**:

```asm
~procProc(Int32, Quad):
  ...
  movsd  0x8(%rsp),%xmm0     ; a
  movsd  0x10(%rsp),%xmm1    ; b
  fldl   0x20(%rsp)          ; d -> st(0)
  fldl   0x18(%rsp)          ; c -> st(0), d -> st(1)
  ret
```

Место `.call` (скомпилировано под `Proc(Int32, Nil)`) зовёт косвенно и
не выталкивает **ничего**:

```asm
__crystal_main:
  mov  0x58(%rsp),%rax
  mov  0x6c(%rsp),%edi       ; аргумент
  call *%rax                 ; <- вызываемый пушит st(0)/st(1)
  jmp  ...                   ; <- ни fxch, ни fstp: слоты утекли
```

После восьми утёкших слотов любой возврат структуры через x87
переполняет стек; `fldl` выдаёт QNaN indefinite.

## Ожидаемое поведение

Либо

- неявная коэрция `Proc(*T, R) -> Proc(*T, Nil)` генерирует
  обёртку, которая вызывает исходное замыкание и корректно
  отбрасывает его возврат, либо
- места `.call` у проков с возвратом Nil выталкивают всё, что
  оставила конвенция вызываемого.

Как минимум — ограничение на этапе компиляции: ковариантность к
`Proc(*T, Nil)` должна отклоняться (или корректно обрабатываться),
когда `R` — структура, не возвращаемая в регистрах по конвенции
платформы.

## Заметки

- Идентично воспроизводится на самосборке 1.21.0/LLVM 20 и
  официальном 1.22.3/LLVM 22 — это не регрессия LLVM.
- Та же дыра достижима через захватываемые блоки: параметр
  `def foo(&block : X ->)` молча принимает блок, чьё последнее
  выражение возвращает структуру.
