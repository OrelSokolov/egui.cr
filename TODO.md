## Мерцание при ресайзе прозрачного окна (bin/terminal, splash) — частично закрыто

**Статус.** Реализовано направление 1 — `_NET_WM_SYNC_REQUEST` в шиме
(классический XSync-счётчик, как ожидает mutter/kwin): см.
`backend/sokol_shim.c` (`sh_x11_sync_request_*`) и патч
`egui_cr_x11_event_hook` в `vendor/sokol/sokol_app.h`. Свойство
`_NET_WM_SYNC_REQUEST_COUNTER` публикуется, целевой serial читается из
ClientMessage, счётчик подтверждается в конце каждого кадра (`sh_frame_cb`).
Осталось проверить руками на живом ресайзе под mutter/XWayland —
симулировать интерактивный ресайз через XTEST в этом окружении нельзя
(WM-грабы не видят синтетический ввод), см. ниже «Проверка».

**Симптом.** При медленном ресайзе окна терминала (`bin/terminal`,
`transparent: true`) появляется мерцание: свежераскрытая полоса на один+
кадр вспыхивает полностью прозрачной — сквозь неё видно рабочий стол.
Чаще при **увеличении** окна (при уменьшении новой площади нет — контент
просто обрезается; подтверждено наблюдением, при уменьшении не
воспроизводится).

**Диагноз (по коду, без изменений).** Не петля кадров — она целостная
(события → один кадр → свап). Проблема структурная: окно получает новый
размер **раньше**, чем существует кадр этого размера.

1. Ресайз в X11 несинхронизирован с рендером: WM меняет размер X-окна
   мгновенно и сам; приложение узнаёт постфактум (`ConfigureNotify` →
   `RESIZED` в следующей итерации петли, `vendor/sokol/sokol_app.h`
   `_sapp_x11_update_dimensions*` — размер поллится раз в кадр через
   `XGetWindowAttributes`). До реализации `_NET_WM_SYNC_REQUEST` (см.
   «Статус») между «окно выросло» и «свап с буфером нового размера
   показан» всегда есть ≥1 скомпозированный кадр, где новой области
   нечем рисовать.
2. Дыру закрывает только background pixel окна: `set_clear_color`
   каждый кадр синхронизирует фон X-окна с цветом очистки
   (`XSetWindowBackground`, `backend/sokol_shim.c`). У непрозрачных
   приложений там `panel_fill` — полоска неразличима. У `transparent:`
   приложений clear color `(0,0,0,0)` (`src/egui/backend/sokol.cr`,
   `paint_frame`), фон пакуется с **альфой 0** на depth-32 ARGB-визуале
   — раскрытая полоса полностью прозрачная, хотя в устоявшемся кадре
   её закрывает непрозрачная панель (меню/табы/статус) или
   полупрозрачная сетка.
3. XWayland (GNOME/mutter) усугубляет: композитор презентует поверхность
   нового размера со старым буфером + прозрачной каймой; форс DRI2
   (`LIBGL_DRI3_DISABLE=1` в `backend/sokol_shim.c`) добавляет
   пересоздание буферов на каждом изменении размера. История погони за
   стояньями свапа при ресайзе — `tmp/sokol-resize-revert-backup.patch`.

**Проверка диагноза.**
- `bin/notepad` (opaque): та же полоска вспыхивает `panel_fill` —
  мерцание неразличимо.
- `bin/splash` (transparent): должно мерцать так же, как терминал.
- Мерцание только при увеличении, не при уменьшении.

## Атласы глифов заканчиваются; утечка памяти на шрифтах (font selector)

**Симптом.** В `bin/widgets_gallery` (вкладка Widgets → Select box,
каталог ~1500 системных семейств) прокрутка/выбор шрифтов: через
~десяток выбранных семейств текст перестаёт рисоваться, а RSS и VRAM
растут до гигабайт.

**Диагноз (по коду).** Архитектура «один атлас на файл шрифта»
рассчитана на пару шрифтов в приложении и не масштабируется:

1. Каждый `AtlasFonts` (стек) владеет **собственным** `GlyphAtlas`
   2048²×RGBA = **16 МиБ CPU + 16 МиБ GPU-текстуры**, независимо от
   того, сколько глифов реально испечено (обычно десятки)
   (`src/egui/backend/text.cr:981`, `GlyphAtlas#flush` →
   `egui_cr_atlas_create`).
2. В C-шиме жёсткий кап `EGUI_CR_MAX_ATLASES 16`
   (`backend/sokol_shim.c:609`): primary + mono + материализованные
   семейства; 17-й `atlas_create` возвращает 0 → `view_id = 0` →
   глифы рисуются в несуществующую текстуру, текст просто пропадает.
   Это и есть момент «перестают отображаться».
3. Утечка: отложенные семейства материализуются при первом рисовании
   и кэшируются **навсегда** (`@@materialized` / `@@named_fonts`,
   `src/egui/backend/sokol.cr:655–689`), destroy-path для атласов в
   шиме отсутствует вовсе («Atlases live for the process lifetime…
   no destroy path is needed»). 50 шрифтов ≈ 50×(16 МиБ CPU +
   16 МиБ VRAM + .ttf-данные) ≈ 1.6+ ГиБ памяти. GC помочь не может:
   на стек держат вечные ссылки реестров.
4. Внутри одного атласа глифы не освобождаются никогда — только
   полный wipe при переполнении (`reset_if_full`).

**Как это решают другие (проверено по исходникам).**

- **upstream egui** (`egui-upstream/crates/epaint`): **один общий
  атлас на ВСЕ шрифты** — `FontsImpl` владеет единственным
  `TextureAtlas`, каждый `FontFace` кладёт глифы в него. Атлас растёт
  по высоте (ширина = `max_texture_side`, до 16K; стартует с 32px).
  Глифы индивидуально не вытесняются; когда `fill_ratio() > 0.8`,
  `Fonts::begin_pass` **пересоздаёт атлас и все кэши целиком**, после
  чего живой набор ребейкается по требованию. Это и есть ring buffer
  уровня атласа: в памяти остаётся только то, что реально на экране.
  Galley-кэш — LRU по generation-счётчику кадров (`CachedGalley`).
- **Qt**: per-`QFontEngine` glyph caches (`QTextureGlyphCache`) с
  LRU-вытеснением; загрузка/выгрузка шрифтов — явные
  `addApplicationFont`/`removeApplicationFont`; неиспользуемые
  движки чистит `QFontCache` (LRU + таймер).
- **Java (LibreOffice)**: `FontStrike` держится слабыми ссылками —
  неиспользуемые страйки собирает GC. Философия «пометь мусором —
  сборщик освободит» работает только когда ничего, кроме GC, не
  держит ссылок; у нас это условие сейчас нарушено (п. 3).

**Предлагаемое решение.**

Фаза 1 — архитектурная (закрывает и кап, и утечку):

1. **Один общий `GlyphAtlas` на бекенд** (владелец — реестр Sokol, не
   отдельный стек): `AtlasFonts` получают ссылку на общий атлас
   вместо своего. GPU-текстура одна, `EGUI_CR_MAX_ATLASES` перестаёт
   быть фактором, память GPU фиксирована. Размер — 2048² или 4096²
   (64 МиБ, ~400 шрифтов превью на атлас против ~100 при 2048²);
   можно расти по высоте, как upstream.
2. **Epoch-счётчик на атласе**: `reset` инкрементирует epoch; каждый
   `AtlasFonts` при `glyph()` сверяет запомненный epoch и чистит свой
   `@glyphs` при рассинхроне — иначе чужой reset оставит у соседних
   стеков висячие UV на перезаписанные слоты.
3. **`reset_if_full` поднять на уровень реестра**: в `paint_frame`
   (`sokol.cr:908–920`) после прохода touch, если хоть у одного стека
   флаг — один reset общего атласа и повторный touch **всех** text
   команд кадра (сейчас reset+retouch локальны в пределах одного
   стека и с общим атласом стали бы некорректны).
4. **LRU-вытеснение материализованных стеков** («помечаем мусором»):
   `last_used_frame` обновляется в `paint_frame` по фактическому
   набору стеков кадра; при превышении капа живых стеков (напр. 64)
   самый старый выкидывается из `@@materialized`/`@@named_fonts` +
   чистится его глиф-кэш — GC собирает .ttf и кэши, повторная
   материализация при новом обращении просто перечитает файл.
   Primary/mono не вытесняются никогда.
5. Заодно: убрать O(stacks×cmds) в `text_cmds.select` на кадр
   (собрать map стек → cmds за один проход).

Фаза 2 — только если фаза 1 даст трэш ресетов при скролле длинного
списка (ребейк ~экрана шрифтов на каждый reset): настоящий ring
buffer на уровне **глифов** — `last_used_frame` на каждый глиф,
вытеснение самых старых с компакцией вместо полного wipe. Это схема
Qt; upstream egui живёт и без неё.

**Затрагиваемые файлы.** `src/egui/backend/text.cr` (GlyphAtlas,
AtlasFonts: общий атлас + epoch), `src/egui/backend/sokol.cr`
(paint_frame, fonts_for_cmd, materialize_font, LRU),
`backend/sokol_shim.c` (опционально `atlas_destroy` с переиспользованием
слотов), спеки `spec/atlas_fill_dbg.cr`, `spec/font_chain_smoke.cr`,
`spec/font_fallback_spec.cr`.

**Критерий готовности.** Прокрутить 200+ семейств в widgets_gallery →
Select box: текст не пропадает, RSS/VRAM выходят на плато и остаются
на нём, возврат к ранее показанному шрифту отрисовывается корректно.

## Реализовать редизайн кадрового цикла (loop_redesign.md)

**Задача.** Реализовать план из `loop_redesign.md` — разделение логики
и презентации на два потока со strict ownership. Полный дизайн,
протокол между потоками и риски описаны там; здесь — контрольный
список работ.

**Почему.** Блокирующий `glXSwapBuffers` (XWayland/mutter свап-стабл
~1 с) сегодня замораживает всё приложение целиком: ввод, логику,
PTY — потому что один поток владеет вводом, логикой, GPU-сабмитом и
present одновременно, а планировщик Crystal — гость в C-цикле sokol
(костыли `evented_pass`, `AsyncDialogs.pump`). Экспериментально
доказано (выпиленный adaptive present): однопоточного корректного
цикла с блокирующим свапом не существует. Правильный фикс —
архитектурный: main-поток = весь Crystal, отдельный C-pthread в шиме
= X-connection + GLX + свап. Стабл свапа деградирует из «замерзшего
окна» в «просадку FPS» при живых вводе/логике/PTY.

**Шаги (каждый шипабельный, порядок из loop_redesign.md §5).**

1. Вернуть телеметрию кадров насовсем (`SLOW full frame`,
   `paint+swap`; код в `tmp/sokol-resize-revert-backup.patch`, без
   adaptive-present).
2. Вынести X/GL-цикл в pthread шима: `frame_cb`/`event_cb`
   C-only (tuple → ring → wake pipe), окно создаёт render-поток.
3. Тесселяция в плоский draw list (FramePacket: вершины + draw calls
   + texture deltas) на main-потоке, replay на render-потоке —
   парой с шагом 2, после чего **удалить `evented_pass` и
   `AsyncDialogs.pump` целиком**.
4. Texture delta-протокол (атлас глифов `AtlasFonts#touch/#flush`,
   Svg-кеш растеризации): GL-вызовы — только render-поток.
5. Опционально: вторая X-connection для ввода на main-потоке
   (нулевая латентность ввода во время стабла).

**Ограничения.** Crystal/GC — только main-поток; render-поток — чистый
C (паттерн уже есть: Win32 file-dialog thread). macOS/Win32 первое
время на старом пути (`#ifdef`). Синхронные запросы (clipboard) —
mailbox с ответом.

**Критерий готовности** (loop_redesign.md §7): при свап-стабле ~1 с —
стоп-кадр на экране не дольше стабла, PTY качается, ввод накапливается
и обрабатывается сразу после разблокировки; телеметрия кадров в репо.

**Связка с атласами.** Шаг 4 — естественная точка интеграции с
общим атласом глифов (задача выше): delta-протокол обязан уметь
destroy/переиспользование слотов атласа, что закрывает и
`EGUI_CR_MAX_ATLASES`.
