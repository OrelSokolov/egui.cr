# Crystal без GC: регионы (арены) + RC-куча

> План «тупого» подхода: убрать Boehm GC без borrow checker'а и без ломки языка.
> Ключевая идея: **две кучи + консервативный escape-анализ**. Никаких lifetimes.

---

## 1. Мотивация

- Crystal: все `class` — ссылки на кучу, управляются Boehm GC.
- Основной юзкейс — веб-серверы: объекты живут ровно время обработки запроса.
- Borrow checker (модель Rust) несовместим с философией Crystal:
  - блоки/замыкания повсюду, захват по ссылке;
  - динамическая диспетчеризация через union/virtual types;
  - метапрограммирование (макросы);
  - C-интероп и экосистема завязаны на GC-семантики.
- Альтернатива: **escape analysis + арены + refcounting** для «сбежавших» объектов.

## 2. Базовая модель: две кучи

### Куча 1 — арена на файбер (по умолчанию)

- Bump-аллокатор: связный список страниц по 4 KB.
- Аллокация = `ptr += size` (+ выравнивание). ~5 инструкций.
- Большие объекты (> порога) — отдельные чанки с заголовком.
- Освобождение — ноль инструкций: арена сбрасывается целиком
  при смерти файбера или вручную (`arena.reset`).
- HTTP-сервер сбрасывает арену после каждого запроса (middleware),
  долгоживущие worker-файберы не разрастаются.

### Куча 2 — RC-куча для «сбежавших»

- Тупое правило: если компилятор **не может доказать**, что объект
  не покидает арену → объект аллоцируется в refcounted-куче.
- Over-approximation допустим: даже 40% объектов в RC дешевле Boehm.

## 3. Правила эскейпа (фиксированный список, may-анализ до фикспоинта)

Объект уходит в RC-кучу, если:

1. присваивается в **глобальную или класс-переменную**;
2. захватывается **замыканием, которое убегает** (сохранённым в поле);
3. передаётся во **внешнюю C-функцию** (`lib` fun — может сохранить указатель);
4. отправляется в **канал** (`Channel#send`) или захватывается блоком `spawn`;
5. пишется в поле объекта, который **сам сбежавший** (итерация до фикспоинта).

Всё остальное (локальные переменные, временные объекты, объекты в полях
других аренных объектов) живёт в арене.

Анализ: flow-insensitive may-escape по типизированному AST. Консервативный:
«сомнения → RC». Полная программа и точные типы у компилятора уже есть.

## 4. RC-куча

### Заголовок

```crystal
struct RcHeader
  count : Atomic(UInt32)  # атомарно: fibers могут быть на разных потоках
  type_id : Int32         # для виртуальных типов / финализаторов
end
```

### Release-функции

Генерируются **per exact type** (в Crystal нет стирания дженериков):

```
__rc_release_Foo(obj):
  if obj.header.count.fetch_sub(1) == 1:
    obj.finalize() if defined
    for каждое поле-ссылка obj: __rc_release_поле
    free(obj)
```

Для виртуальных типов (`Foo+`) — слот в vtable (механизм уже существует).

### Циклы

- Циклические ссылки утекают (как в Swift до циклического GC).
- Принимаем в v1. Даём `Weak(T)` для ручного разрыва.
- Опционально позже: детектор циклов под флагом `--debug-cycles`.

## 5. Границы файберов

- `spawn do ... end` — захваченные объекты конвертируются в RC при захвате
  (ретейн): файбер может пережить породивший.
- `Channel#send` — отправленный объект уходит в RC:
  retain при send, release после обработки на приёмной стороне.
  Владение передаётся codegen'ом (встроенные retain/release на границах).

## 6. Детерминированные деструкторы (бонус)

С аренами `finalize` становится предсказуемым:

- при `arena.reset` — прогон списка финализаторов файбера;
- при RC count → 0 — немедленно.

Файловые дескрипторы, сокеты, mutex'ы закрываются детерминированно.
Это selling point режима `--gc=none`.

## 7. API (без нового синтаксиса языка)

Базовая модель полностью неявная. Три ниши — три фабрики в stdlib:

```crystal
# 1. Именованные арены (регион, живущий дольше файбера)
arena = Arena.new
arena.use do
  index = Parser.build_index(source)  # всё аллоцированное тут — в index
  index.dump("index.bin")
end
arena.reset

# 2. Ручной эскейп в RC-кучу
config = Heap(Config).new(settings)
App.config = config

# 3. C-интероп (глубокая копия в RC-кучу)
data = Heap.copy(payload)
LibFoo.store_callback(->callback, data.as(Void*))
```

### Чего сознательно НЕ делаем

```crystal
# ❌ не будет: lifetimes/арены в сигнатурах типов
name : arena String
def parse(src : &String, arena a) : Tree(a)
```

- Crystal = «компилятор выводит всё» — аннотации ломают философию языка.
- Вся информация для вывода у компилятора уже есть (целая программа,
  точные типы, граф вызовов).
- Неявная модель не может быть обманута юзером: либо работает,
  либо консервативно падает в RC. Способа выстрелить в ногу нет.

## 8. Флаги компиляции

```
crystal build app.cr                  # Boehm, как сейчас (дефолт)
crystal build app.cr --gc=none        # арены + RC, без LibGC вообще
crystal build app.cr --stats=arena    # страниц аллоц/освоб на файбер
```

Режим `--gc=none` — полная линковка без Boehm: mmap страниц арены.

## 9. Что ломается / ограничения

- **C-библиотеки, сохраняющие указатели** (sqlite callbacks, curl) —
  юзер обязан использовать `Heap.copy` / `LibC.malloc`. Документируем (~5% кейсов).
- **`Pointer(T).malloc`** — не трогаем, ручное управление как раньше.
- Семантика `Object#finalize` меняется (детерминированно — скорее плюс).
- Код, завязанный на «объект жив вечно, потому что GC», может обнаружить
  use-after-free → поэтому дефолт остаётся Boehm.
- Циклические RC-ссылки утекают (v1 — принимаем).

## 10. MVP-план (по возрастанию боли)

| Шаг | Что | Оценка |
|-----|-----|--------|
| 1 | `Arena` в рантайме (bump + страницы + reset) | 1 день, ~200 строк |
| 2 | Флаг `--gc=none`: аллокации классов → арена `Fiber.current.arena` | 1 неделя (точки аллокации централизованы в codegen) |
| 3 | Прогон финализаторов при reset | 2 дня |
| 4 | Escape-анализ (6 правил, may-анализ по typed AST) | 2–3 недели — **основная работа** |
| 5 | RC-куча + retain/release в codegen | 2 недели |
| 6 | Конвертация на границах `spawn` / `Channel` | 1 неделя |
| 7 | Бенчмарк: Kemal hello-world vs Boehm | — |

## 11. Почему это будет быстро

Аллокация в арене (ассемблер):

```asm
mov rax, [fiber + arena_ptr]
lea rcx, [rax + size + 7] & ~7
cmp rcx, [fiber + arena_end]
ja  .slow_path        # редко: новая страница
mov [fiber + arena_ptr], rcx
```

~5 инструкций, никаких free-листов, никаких пауз. Деаллокация — 0 инструкций.
Модель «арена на запрос» не трёт память и дружит с CPU-кэшем.
Гипотеза: GC-free HTTP-сервер на такой схеме конкурентен с Rust/tokio
по throughput на мелких запросах.

## 12. Главный риск

Не анализ и не codegen, а **экосистема**:
- привычка «объект жив вечно, потому что GC»;
- неявные эскейпы через глобальное состояние;
- детерминированный `finalize` меняет ожидания.

Социальная работа: чёткий миграционный гайд, Boehm как дефолт
в обозримом будущем, `--gc=none` — как opt-in для горячих сервисов.
