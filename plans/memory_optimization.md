# Память: план оптимизаций (macOS, footprint как в Activity Monitor)

> **Статус: план** (частично реализовано: опция `msaa:` — см. §4, шаг 0).

## 1. Замеры-ориентиры (эта машина, macOS 26, Retina, живые окна)

| Приложение | MSAA | phys_footprint | Графика (vmmap: owned unmapped graphics + IOAccelerator + IOSurface) |
|---|---|---|---|
| Нативный AppKit (`oracle/macos/render gallery`, Swift/CoreAnimation) | — | **29 МБ** | ≈0 — композитит WindowServer, память не списывается на процесс |
| egui.rs (eframe 0.27, glow/GL, дефолт) | нет (`epi.rs:394`: `multisampling: 0`) | **101 МБ** | **~60 МБ** (42 + 7.6 + 9.6) |
| egui.rs + `multisampling: 4` | 4x | ~101–116 МБ (peak) | MSAA добавляет лишь ~15 МБ |
| egui.cr `bin/hello` (sokol GL, дефолт) | 4x | **332 МБ** | ~250 МБ (164 + 55 + 29) |
| egui.cr `bin/hello`, `msaa: false` | нет | **227 МБ** | ~156 МБ |
| egui.cr `bin/macos_gallery` (дефолт) | 4x | **380 МБ** | ~248 МБ + куча GC ~95 МБ (больше начертаний/текстур, чем hello) |

Разбивка hello `msaa: false` (227 МБ): ~156 МБ графика/драйвер + ~46 МБ
куча Boehm GC (атлас глифов 2048² RGBA = 16 МБ + шрифты + структуры) +
~3 МБ Crystal-рантайм + прочее.

Ключевой вывод: тезис «~150 МБ за GL-контекст неизбежны» **опровергнут
замером eframe** — на том же GL его графика-аллокации ~60 МБ. Разрыв
~95–100 МБ — разница конфигурации контекста (sokol_app vs glutin), а не
плата за GL как таковой.

## 2. Корневые причины (гипотезы, по убыванию ожидаемого эффекта)

1. **Pixel format / свопчейн sokol_app.** Sokol запрашивает для
   default-framebuffer depth+stencil (UI-рендеру не нужны), а eframe/
   glutin — нет. Также возможны: количество backing-буферов окна,
   размер aux/backing store, swap interval. Кандидат на ~60–95 МБ из
   разрыва.
2. **Аномальная цена MSAA: +105 МБ у нас против +15 МБ у eframe.**
   Тоже похоже на конфигурацию свопчейна/resolve-буферов, а не на природу
   MSAA (окна сопоставимого размера, Retina 2x в обоих случаях).
3. **Атлас глифов 2048² RGBA** (`src/egui/driver/text.cr`): 16 МБ CPU +
   ~16 МБ GPU. egui.rs ходит с R8-атласом (только покрытие) — 4+4 МБ.
4. **Фиксированный размер атласа** — 2048² с первого кадра, даже для
   hello, которому хватило бы 1024².
5. Куча gallery (~95 МБ против 46 МБ у hello) — больше начертаний и
   юзер-текстур; отдельная разведка (профиль кучи), не блокер.

## 3. Цель

Hello: **227 → ~100–120 МБ** (паритет с egui.rs). Пол ниже ~100 МБ
недостижим в архитектуре «процесс владеет GPU-контекстом»; 29 МБ
нативного AppKit — другая модель (композитинг WindowServer), не цель.

## 4. Шаги (порядок = убывание эффекта/риска)

### Шаг 0 (сделано): опция `Egui.run(app, msaa: false)`
`backend/sokol_shim.c`: `egui_cr_sapp_run`/`egui_cr_start` принимают
флаг; `sample_count = (transparent || !msaa) ? 1 : 4`.
`src/egui/driver/sokol.cr`: опция задокументирована. Эффект: −105 МБ.
Решение «делать ли `msaa: false` дефолтом» — отдельно, после шага 1
(если цена MSAA упадёт до eframe-уровня, дефолт можно оставить 4x).

### Шаг 1: конфигурация GL-контекста до уровня eframe (главный шаг)
- Сравнить запрашиваемый NSOpenGL pixel format у sokol_app и glutin
  (eframe): depth/stencil, buffer count, backing store, swap interval.
- Пробовать: `sapp_desc.depth_format/stencil_format = NONE` на UI-пути
  (осторожно: 3D-пайплайн crystal3d требует depth — оставить режим для
  него), уменьшить backing-буферы.
- Ожидание: **−60…−95 МБ** у графики; MSAA-дельта +105 → ~+15 МБ.
- Проверка: footprint hello и macos_gallery до/после; смоук-спеки
  (core_spec, hotkeys_spec — 212 примеров); визуально Retina-текст.

### Шаг 2: R8-атлас глифов (−24 МБ)
- Формат текстуры RGBA8 → R8 (только coverage; альфа уже так и хранится:
  `alpha = 2c − c²`, цвет кладётся вершиной) — `text.cr` + шейдерная
  выборка `.r` в шиме.
- egui.rs годами так делает — подход проверен.
- Эффект: 16→4 МБ CPU + ~16→4 МБ GPU. Риск низкий, спеки есть.

### Шаг 3: ленивый/растущий атлас (−12…24 МБ на старте)
- Начинать с 1024², расти до 2048²/4096² при переполнении.
- Сложнее: перекомпоновка кэша глифов при росте (перестройка UV).
- Эффект: у hello/CJK-лёгких приложений атлас так и остаётся 4+4 МБ.

### Шаг 4 (опционально): Metal вместо GL (`SOKOL_METAL`)
- Теперь ниже по приоритету: если шаг 1 срежет драйверную разницу,
  выигрыш Metal'а неочевиден, а работа — средняя (шим + проверка
  скриншот-пути: вендорная sokol без `sg_read_pixels`, прямой
  `glReadPixels` есть только в GL-ветке).
- Возвращаться к идее только после шага 1 с замером «что осталось».

## 5. Чего НЕ делать

- **Своя отрисовка взамен sokol_gfx** — ≈0 МБ экономии: sokol_gfx ничего
  весомого не держит; ~60 МБ (после шага 1) — цена контекста и свопчейна
  независимо от того, кто создаёт контекст. При этом «выкинуть только
  gfx» нельзя: окно/события/клипборд/drag-drop/Android — это sokol_app,
  пришитый к шиму в 8 местах через `sapp_macos_get_window()`.
- Гоняться за 29 МБ нативного AppKit — другая архитектура (композитинг
  WindowServer, разделяемые страницы AppKit).
