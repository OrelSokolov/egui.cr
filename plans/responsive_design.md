# Responsive design — липкий form factor + мягкая деградация по ширине

> **Статус: план** (не реализовано). Контракт зафиксирован в README,
> секция «Responsive design expectations».

## 1. Постановка

Сложные виджеты (меню — первый кандидат) имеют один layout-путь,
зашитый в кристалл-код: `ctx.menu_bar` всегда рисует горизонтальную
полосу (`src/egui/containers/menu.cr:103`), `menu_button` — кнопку с
попапом. На мобилке/вертикальном экране это не работает. Стили (ECSS)
меняют вид, но не layout-скелет — и не должны.

Два независимых механизма (обсуждено и согласовано):

1. **Form factor липкий**: `:desktop` / `:mobile`, определяется один
   раз при старте (таргет сборки или явный оверрайд). Никогда не
   пересчитывается от размера окна: десктопное приложение при сужении
   окна не «превращается в телефон» — пользователи этого не ожидают
   (VS Code прячет сайдбар, но не растит гамбургер-дроер).
2. **Ширина — мягкая деградация внутри вида**: overflow-меню «⋯»,
   коллапс панелей, перенос тулбаров. Идентичность вида не меняется.
   На мобилке ориентация может перестраивать layout внутри
   мобильного вида.

Архитектурный выбор — **вариант 1 («двойник внутри виджета»)**: API
`ctx.menu_bar { |bar| … }` не меняется; внутри виджет читает
`ctx.form_factor` и переключает рендерер. Блок приложения выполняется
один и тот же — immediate mode и так перезапускает его каждый кадр,
«пере-рендер в другом контейнере» бесплатен. Прецедент режимного
флага в кодовой базе уже есть: `Ui#menu_popup_key`
(`src/egui/containers/menu.cr:227`) меняет поведение `menu_button`,
когда он вложен в попап.

Логика (акшены, хоткеи через `ctx.hotkeys` / `fire_action`,
включённость пунктов) уже отвязана от рисования и остаётся общей.

## 2. Шаги

### Шаг 1. `FormFactor` на Context + оверрайды

- `enum Egui::FormFactor; Desktop; Mobile; end` (в `context.cr` или
  отдельном `form_factor.cr`).
- Разрешение один раз, при создании `Context`, по приоритету:
  1. явный оверрайд `Egui.form_factor = :mobile` (module-level setter,
     для спеков/скриншотов/инспектора);
  2. CLI-флаг `--form-factor mobile` — расширить `Egui::CLI.parse`
     (`src/egui/cli.cr:23`) по образцу `--page`: возвращать
     `form_factor` в NamedTuple, неизвестные флаги по-прежнему
     проходят в приложение нетронутыми;
  3. compile-time: `flag?(:android)` → `:mobile`;
  4. дефолт `:desktop`.
- `Context#form_factor : FormFactor` — геттер без сеттера
  (переназначение в рантайме не предусмотрено; оверрайд читается
  только на старте).
- Спека `spec/form_factor_spec.cr`: порядок разрешения, дефолты,
  CLI-парсинг (`--form-factor mobile`, `--form-factor=mobile`, bare
  `--form-factor` игнорируется — как `--page`).

### Шаг 2. `Context#menu_bar` — диспетчер по form factor

`menu.cr`:

- Текущее тело `menu_bar` выносится в приватный
  `menu_bar_desktop(&block)` без изменений поведения.
- `menu_bar` проверяет `ctx.form_factor`:
  - `:desktop` → `menu_bar_desktop`;
  - `:mobile` → `menu_bar_mobile` (шаг 3).
- На `Ui` добавляется режимный флаг `menu_mode : Symbol?`
  (`:drawer`/`nil`) — по образцу `menu_popup_key`. В режиме `:drawer`:
  - `menu_button` рендерится как секция-аккордеон (строка с
    шевроном, клик раскрывает/сворачивает вложенные пункты; состояние
    — per-id в `ctx.memory`, как у `CollapsingHeader`,
    `src/egui/widgets/collapsing_header.cr`);
  - `menu_item` — полноширинная строка; клик закрывает дровер
    ВМЕСТО попапа (проверять `menu_mode`, а не только
    `menu_popup_key` в `menu_item_impl`, `menu.cr:335`).
- Hover-switch логика (переключение корневых меню при наведении,
  `menu.cr:182`) в режиме `:drawer` не выполняется — мышь на мобилке
  не главный ввод.

### Шаг 3. Мобильный рендерер: гамбургер + дровер-сайдбар

- Компактная полоса той же высоты, что бар (чтобы `top_panel`-логика
  приложений не поехала): иконка-гамбургер (`Icons`, есть
  `menu`-группа — проверить `src/egui/widgets/icons.cr`) + опционально
  заголовок приложения.
- Клик по гамбургеру открывает дровер: `ctx.side_panel(:left,
  "menu_drawer", layer: <overlay-слой>)` — слой поверх контента со
  скримом, НЕ переflowing available_rect (иначе контент будет
  прыгать). Скрим-клик и `Esc` закрывают; клик по пункту закрывает
  (шаг 2). Открытость — per-id в `ctx.memory.areas`/`Memory`, как у
  попапов.
- Внутри дровера — `ScrollArea` (меню длиннее экрана) + тот же блок
  приложения: `yield ui` с `ui.menu_mode = :drawer`.
- Styling: классы `menu.drawer`, `menu.accordion`, `menu.row` в
  `default_theme.cr` + StyledPart-двойники (`MenuDrawerPart` и т.д.),
  чтобы инспектор и ECSS работали как с остальными виджетами.
- Гамбургер — тоже StyledPart (`menu.hamburger`), чтобы
  кастомизировать.

### Шаг 4. Деградация десктопного бара по ширине (overflow «⋯»)

- Только в `:desktop`. Корневые кнопки, не влезающие в ширину бара,
  прячутся в последний пункт «⋯» (вложенный попап со списком
  «недовольных» рут-меню как подменю).
- Immediate-mode паттерн egui «ширина с прошлого кадра»: natural
  width каждой рут-кнопки пишется в per-id память; на следующем кадре
  cutoff по накопленной сумме. Однокадровый лаг при ресайзе — норма
  (так работает и upstream egui для sizing).
- Спека `spec/menu_overflow_spec.cr`: узкое окно в headless-прогонах,
  assert что «⋯» появился и пункты доступны через него.

### Шаг 5. Спеки, скриншоты, дока

- `rake spec` зелёный; новые спеки шагов 1–4 headless (по образцу
  `spec/menu_spec.cr`).
- Прогон руками: `./bin/notepad --form-factor mobile`,
  `./bin/paint --form-factor mobile` на десктопе.
- Скриншоты: добавить мобильные кадры в `scripts/make_screenshots.py`
  (deep-link через существующий `--page` + новый `--form-factor`) —
  опционально, отдельным шагом.
- README: секция «Responsive design expectations» уже описывает
  контракт; после реализации убрать «плановость» формулировок, если
  появится, и вписать фактические API-имена.

## 3. Что НЕ делаем (зафиксировано, чтобы не скатиться)

- Никакого переключения form factor по viewport/ориентации В ОСНОВНОМ
  виде. Ориентация на мобилке — будущий механизм ВНУТРИ `:mobile`
  (например, side-panel в landscape), отдельным планом.
- Никаких media queries в ECSS для смены layout-скелета: стили
  подстраивают вид (паддинги, шрифты, цвета) per form factor —
  классы вида `menu.drawer` просто существуют только в мобильном
  рендере, каскад обычный.
- Никакого публичного `MenuSpec`/декларативной модели: блок
  приложения и есть модель, рендереры внутри виджета. Если позже
  понадобится третий вид рендера или не-визуальное использование —
  тогда и вынесем.
- Мобильные двойники остальных сложных виджетов (select_box,
  tableview, даты) — по мере надобности, каждый по той же схеме
  «двойник внутри + `ctx.form_factor`».

## 4. Риски и открытые вопросы

- **Слой дровера**: `side_panel` принимает `layer`, но надо проверить,
  что overlay-слой не клипается и скрим ловит клики мимо панели
  (механика попапов `ctx.popup` может оказаться проще — дровер как
  «попап, прилипший к левому краю»). Решить на шаге 3 сперва.
- **Состояние аккордеонов vs `memory.menu_open`**: у попапов
  one-open-правило через `menu_open`; аккордеонам нужно независимо
  раскрываемое состояние (несколько секций открыто одновременно —
  как в нативных мобильных меню). Не смешивать.
- **Дровер и window frame**: у borderless-окон свой caption в
  `top_panel` — на мобилке caption свой (жесты/статусбар), это вне
  скопа плана; пока мобильный `menu_bar` просто рисуется под
  caption'ом как обычно.
- **Повторный `begin_frame` для дровера**: блок приложения в дровере
  выполняется в том же кадре, что и обычный — id-коллизии между
  «баром» и «дровером» исключены, потому что в мобильном виде бар
  рендерит ТОЛЬКО гамбургер, блок не выполняется дважды за кадр.
