# MVC-разрез egui.cr и слияние с positron.cr

Статус: на ревью у автора. Это итог обсуждения (не реализация).

## 1. Цель

Два проекта (egui.cr — immediate-mode на sokol, positron.cr — retained
на WebView) существуют для сравнения подходов. Чтобы сравнение стало
честным, а разработка — быстрой, обе кодовые базы сводятся к одной
архитектуре: **общие интерфейсы, разные реализации**. Паттерн — старый
надёжный MVC (Rails-стиль): приложение = действия над ресурсами,
контроллеры с роутами, CRUD, полная тестируемость логики без UI.
Никаких новых изобретённых идей — то, чем все уже пользуются.

Главный измеримый критерий: скорость накидывания форм и простых
приложений должна быть не хуже, чем через JS+CSS. Если фреймворк этого
не даёт — смысла в нём нет.

## 2. Словарь (термины зафиксированы)

| Термин | Что это | Где сейчас |
|---|---|---|
| **Frontend** | view: страницы, EXML-компоненты, виджеты, роутер окна | egui: `widgets/`, `containers/`, `router.cr`, `exml.cr` |
| **Backend приложения** | вся логика: Router, контроллеры, ресурсы, CRUD, стор, джобы, модель | positron: `http_router.cr` и др. — уже написан |
| **Driver** | отрисовка: окно, цикл кадров, GPU, ввод | egui: `backend/sokol.cr` (переименовать); positron: `Host` + EventLoop + WebView (переименовать) |
| **Системные порты** | clipboard, dialogs, tray, camera, ... | egui: `system_ports/`; positron: 16 плагинов — одно и то же, криво названо |
| **Transport** | единственная дыра между frontend и backend приложения | нет; вводится |

Бывший `backend/` в egui.cr перестаёт называться бэкендом — он
**драйвер**. Слово «бэкенд» закреплено за слоем логики приложения.

## 3. Общая архитектура

```
┌─ ДРАЙВЕР ──────────────────────────────────────────┐
│ sokol (egui) / Host+EventLoop+WebView (positron)   │
│ окно, цикл кадров, GPU, ввод → RawInput            │
│ интерфейс: run / stop / wake / run_on_main /       │
│            gui_context?                            │
└───────────────────────┬────────────────────────────┘
                        │ кадр: begin_frame / update / end_frame
┌───────────────────────┴────────────────────────────┐
│ FRONTEND                                            │
│ страницы (роутер окна) → EXML-компоненты → виджеты │
│ умеет ТОЛЬКО: читать store, звать request          │
└───────────────┬────────────────────────────────────┘
                │ Transport#call(Request, &on_done) — единственная дыра
┌───────────────┴────────────────────────────────────┐
│ BACKEND ПРИЛОЖЕНИЯ (общий код обоих проектов)      │
│ Router → Controller → действие / ресурс (CRUD)     │
│ State — единственный владелец данных               │
│ Async — фоновые джобы (из AsyncWork positron)      │
│ Model — внешний ORM-шард, фреймворку безразличен   │
└───────────────┬────────────────────────────────────┘
┌───────────────┴────────────────────────────────────┐
│ СИСТЕМНЫЕ ПОРТЫ — общий шард (1:1 с positron)      │
└─────────────────────────────────────────────────────┘
```

Ключевое правило разреза: **frontend не знает ни одного типа backend**.
У него нет доступа к Router, к контроллерам, к модели — только
`request`. Граница существует в типах, видна глазом и физически не
обходится, хотя передача виртуальная (в памяти, нулевая цена).

## 4. Правило данных

Всё состояние, которое переживает кадр, — это данные. Данные живут в
backend. Виджет — экранка и кнопки: рендерит store, шлёт request.
Без исключений, поэтому один паттерн покрывает оба типа приложений:

| Приложение | Данные (backend) | Виджет (frontend) |
|---|---|---|
| Блог-админ с базой | посты, пользователи (ORM) | таблица, формы |
| Блокнот | документ, курсор, dirty-флаг | textarea, меню |
| Терминал | буфер скроллбэка, PTY-сессия | экранка терминала, ввод |

«Фабрика фич» из positron переносится целиком: сложное data-приложение
с джобами собирается по той же схеме, что и блокнот.

## 5. Transport — интерфейс и протокол

Конверт — `Request`/`Response` из роутера positron (`http_router.cr`),
байт-в-байт: контроллеры обоих фреймворков видят одинаковые типы,
positron свой формат всё равно сериализует.

```crystal
struct Request
  getter method : String                # GET / POST / PATCH / DELETE
  getter path : String                  # "/posts", "/doc/insert", "/term/stdin"
  getter query : Hash(String, String)
  getter body : JSON::Any
end

struct Response
  getter status : Int32                 # 200 / 404 / 422 / 500
  getter body : JSON::Any
  def ok? = status < 400
end

abstract class Transport
  # Ответ — только колбэком, никогда синхронно.
  abstract def call(request : Request, &on_done : Response ->) : Nil
end
```

Реализации:
- **egui — `InProcessTransport`**: конверт летит по ссылке (ноль
  сериализации), обработка в файбере, `on_done` доставляется МЕЖДУ
  кадрами + `Driver.wake` → следующий кадр видит результат.
- **positron — `BridgeTransport`**: JSON через мост WebView, ответ —
  resolve промиса в JS. Разница между реализациями — только где живёт
  `on_done`.

Вью-facing API — не «транспорт», а запрос (как `Positron.request` в JS):

```crystal
Egui.request "POST", "/posts", title: "Привет", tags: ["a"] do |resp|
  # ошибки никогда не райзят — всегда status в resp
end
```

Транспорт несёт **только намерения** (клики, сабмиты — десятки раз в
минуту; JSON-налог ничтожен). Потоковые данные кадра (скроллбэк
терминала, текст документа) идут через store — это бесплатно.

Сознательно НЕТ в транспорте:
- **событий backend→frontend** — уведомления это работа стора
  (`store.subscribe`), иначе две шины и каша; в positron `emit_to_js`
  становится просто подписчиком стора;
- **синхронного вызова** — блокировка на фрейм-файбере = замороженное
  окно; гард как у `.value` в positron;
- **отмены запросов** — v1 без неё; при необходимости добавляется id
  в конверт, интерфейс не ломается.

## 6. Backend-слой: Router → Controllers → Resources

Хребет приложения. Роутер — не цель, а механизм ввода контроллеров;
контроллеры — для ресурсов и действий. Приложение = «делай действие»
или «редактируй ресурс», и всё стандартизировано: карта приложения
читается из `resources "posts", PostsController` + списка экшенов.
Портируется из positron (`http_router.cr`: get/post, namespace,
Controller + resources, middleware, флаг heavy для параллельных
обработчиков). Одна страница ≡ один контроллер: `root/posts` ↔
`PostsController`. Роутер страницы (навигация окна) и роутер команд —
разные роутеры с разными ролями, оба остаются, каждый в своём слое.

EXML-компоненты: экшены (`on_click="save"`) после миграции стреляют
только через request — сегодня механизм тот же, но стреляет кодом
приложения напрямую.

## 7. State — хранилище состояния (кандидат, детали на проработке)

Что есть сейчас — три механизма на спектре «предсказуемость ↔ простота»:

| | Механика | Изменение состояния |
|---|---|---|
| Redux | стор + действия + чистые редьюсеры | событие (dispatch) |
| positron StateManager | плоский словарь + EventBus-уведомление | присваивание + письмо в шину |
| сигналы egui (`reactive.cr`) | типизированные ячейки + auto-подписка | присваивание в сигнал |

Имена зафиксированы:

```crystal
class State                    # бэкенд: dispatch / [] / subscribe
  def dispatch(action : String, payload) : Nil  # ЗАПИСЬ = событие
  def [](key : String) : StateValue
  def subscribe(key : String, &)
end

abstract class StateView       # фронтенд: [] / subscribe — и всё
  abstract def [](key : String) : StateValue
  abstract def subscribe(key : String, &) : Nil
end
```

Почему `dispatch`, а не `set`: запись — событие («случилось
posts/loaded»), а не присваивание. Отсюда лог изменений, время-
travel в инспектор egui (он уже есть), воспроизводимость. `commit`
из Vuex не берём — там двойная семантика (commit=мутация,
dispatch=экшен).

Кандидат механики: интерфейс действий из редакса (`dispatch`) +
внутренности из сигналов: обработчик действия пишет в типизированные
ячейки, перерисовка прицельная. positron'овский `state.changed →
JS-патч` = подписчик стора. Чистые редьюсеры полного редакса — нет:
стор в одном месте, гонок нет, чистота ради чистоты = церемония.

Критерии к интерфейсу: (1) один для обоих фронтов — egui-подписка =
repaint, positron-подписка = патч JS-стейта; (2) изменения только
через dispatch — иначе у контроллеров появится второй, обходной путь
писать в стор; (3) джобы (Async) коммитят тем же dispatch.

**Владелец состояния — бэкенд (обязательное правило).** Сторож
ресурсоёмкой операции — контроллер, а не кнопка: двойной клик, второе
окно, CLI обходят фронтендную защиту. Контроллер держит реестр задач
(готовая механика — `async_job` из positron: хэндл с `done?`/
`cancelled?`, токен pause/cancel) и на повторный `POST /jobs/x`
отвечает 409 / `{job_id, status: "running"}`. Фронтендный стейт —
одноразовый кэш: его можно выкинуть и восстановить из стора.
Фронтенду принадлежит только эфемерная виджетная мелочь (фокус,
скролл — `Memory` по Id, не данные приложения). В positron это
сейчас нарушено: JS-стор — второй владелец, синхронизируемый
событиями; после слияния JS-стор становится чистым кэшем.

**Кто пишет / кто читает:**

| | пишет (dispatch) | читает |
|---|---|---|
| фронтенд | никогда | всегда (StateView — рендер) |
| контроллер | да (результат действия) | да (решения: «задача running?» → 409) |
| джоба (Async) | да (результат фоновой работы) | да (параметры: что делать) |
| порты системы | да (внешние события) | — |
| транспорт | никогда | никогда (только возит request/response) |

Стор — также средство связи ВНУТРИ бэкенда: контроллер ↔ джоба ↔
контроллер координируются через состояние, не зная друг о друге
(реестр задач из примера выше).

**StateView — read-only вид State для фронтенда.** Состояние течёт
назад (к фронту) одним способом, намерения — вперёд (транспортом);
две дыры, обе односторонние.

| | egui | positron |
|---|---|---|
| Реализация StateView | сам State (сигналы внутри) | JS-зеркало из фасада |
| Чтение | по ссылке, бесплатно, срез между записями (pull) | из JS-кэша |
| Синхронизация | не нужна: все записи между кадрами, кадр видит целостный срез | патчи по мосту на `state.changed` (push), старт — гидрация снапшотом |
| `subscribe` | механизм repaint | реактивность Vue: компонент, прочитавший поле, перерисуется сам, когда придёт патч |

JS-зеркало выглядит для компонентов как Pinia/Vuex-стор, но
read-only: пишет в него только мост патчами с Crystal. (Оптимистичные
апдейты «нарисуй сразу, бэкенд подтвердит» — потом, поверх, не в v1.)

**Защита границы «фронт не пишет в State»** — три уровня:

1. Разводка: `State` — не глобальный синглтон; его раздаёт `Egui.run`
   адресно — контроллерам и джобам State, вьюхе StateView. Чтобы
   нарушить, надо протащить State во фронт руками — видно в диффе.
2. Композиция, НЕ наследование: `StateView` — отдельный объект,
   держащий `@state` без геттера; `State` не наследует `StateView`,
   иначе `view.as(State).dispatch` сработал бы. Наружу торчат ровно
   `[]` и `subscribe`.
3. Процессная стена (только positron): у JS-фронта нет
   кристалловских объектов — там защита абсолютная. В egui —
   «заметная», не «абсолютная»: честная цена нулевой сериализации.
   Плюс дешёвый арх-линт: спек, который гоняет вьюхи/страницы и
   падает, если в них встречается `dispatch`.

## 8. Driver

Пять методов, один интерфейс, разные потроха:

```crystal
abstract class Driver
  abstract def run            # цикл
  abstract def stop
  abstract def wake           # «нарисуй кадр» (сейчас Runtime.wake)
  abstract def gui_context?   # «я в фрейм-файбере?»
  abstract def run_on_main(&) # выполнить блок в потоке отрисовки
end
```

- egui: `Backend::Sokol` → `Egui::Driver::Sokol`; `runtime.cr` (три
  глобальные переменные) исчезает — это и был полуфабрикат драйвера.
- positron: `Host` переименовывается в драйвер; там он уже разрезан
  на EventLoopPort (цикл) и WebViewPort (поверхность) — насильно
  резать egui так же не нужно, достаточно общего интерфейса.
- `eval_js` остаётся на WebViewPort positron — в общий интерфейс не
  входит: «чем рисуем» — это и есть то, что отличается по определению.

Разница моделей отрисовки (фиксируется, не «чинится»): в egui Crystal
владеет пикселями (тесселяция, атлас глифов — наш код), в positron
пикселей не видит (WebKit растеризует, Crystal платит сериализацией
за каждое обновление). Это ровно то, что меряет эксперимент.

## 9. Тестирование — три режима, все headless (без окна и GPU)

```crystal
# 1. Бэкенд в лоб: ни фронтенда, ни драйвера
resp = App.router.handle(Request.new("GET", "/posts"))
resp.status.should eq 200

# 2. Фронтенд с фейковым бэкендом: транспорт подменён скриптованным,
#    вьюха гоняется кадрами (Capybara-харнесс egui.cr уже умеет кадры)
fake = ScriptedTransport.new
fake.on("GET", "/posts") { Response.ok(posts_json) }
app = MyPageApp.new(fake)
app.click("Обновить")
app.render
app.label("Пост 1").should be_visible

# 3. Всё вместе headless: настоящий in-process транспорт + настоящие
#    контроллеры (модель подменена) — регресс всего конвейера
#    клик → контроллер → стор → кадр
```

Режим 3 — самый ценный: полный прогон приложения на реальном шве.
В egui.cr для этого есть Capybara; доучить его подменять транспорт.

## 10. Порядок миграции (egui.cr)

Каждая фаза оставляет дерево зелёным (rake spec, примеры собираются).

1. **Каркас backend-слоя.** Порт Router/Controller/Request/Response
   из positron в egui.cr (общий код). Пока без привязки к UI.
2. **Transport + request-сахар.** `InProcessTransport`, доставка
   между кадрами, `Egui.request`. Гард на фрейм-файбере.
3. **Переименование `backend/` → драйвер.** `Backend::Sokol` →
   `Driver::Sokol`, `runtime.cr` → интерфейс `Driver`. Чистый рефакторинг.
4. **Миграция приложений-примеров на MVC.** notepad, terminal,
   таблицы: состояние переезжает в контроллеры+стор, `update` тончает
   до «читай store, шли request». Миграция одного примера = шаблон
   для остальных.
5. **State.** Проработка §7: интерфейс State/StateView/dispatch,
   посадка сигналов внутрь, подписчик positron'а снаружи.
6. **Вынос общих шардов.** Router+Transport+State+Async и системные
   порты — в отдельные shard'ы; positron переезжает на них, своим
   оставляя JS-фронт, webview-драйвер и JSON-мост.

## 11. Чего НЕ делаем

- Никаких новых паттернов ради паттернов — MVC, проверено десятилетиями.
- Никакого прямого вызова Crystal-кода бэкенда из фронтенда — только
  request. Если можно — границу нарушат.
- Никакого JSON на горячем пути egui — сериализация только в мосте
  positron (там она неизбежна) и в конверте редких намерений.
- Никакого DI-контейнера — compile-time выбор реализаций
  (`{% if flag? %}`), как в positron.
- Не тащим чистые редьюсеры, если не докажем пользу.
- Не сводим драйверы к одному коду — общий только интерфейс из 5 методов.
