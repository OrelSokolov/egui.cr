# 0% CPU в idle: патч бэкенда (sokol_app)

## Проблема

Замер `bin/hello` (Linux/X11, окно открыто, ввода нет, 8 секунд):

- ~3.9% одного ядра CPU;
- ~380 пробуждений/сек (voluntary ctxt switches);
- GPU каждый vsync ре-растрит тот же кадр.

Ядро egui.cr в idle уже делает всё правильно (`backend/sokol.cr:421`):
пропускает `app.update` и тесселяцию, переиспускает последний список
команд. Весь остаточный расход живёт в цикле sokol_app.

## Корневая причина

`vendor/sokol/sokol_app.h`, X11-цикл `_sapp_linux_run` (~строка 14297):

```c
while (!_sapp.quit_ordered) {
    int count = XPending(_sapp.x11.display);   // НЕ блокируется
    while (count--) { XNextEvent(...); _sapp_x11_process_event(&event); }
    _sapp_linux_frame();                       // frame_cb + БЕЗУСЛОВНЫЙ glXSwapBuffers
}
```

Два факта:

1. Цикл не блокируется на событиях — такт ему задаёт блокирующийся до
   vsync `glXSwapBuffers` (`_sapp_linux_frame`, строка ~14225). Отсюда
   60 пробуждений/CPU-работ в секунду без всякой причины.
2. Свап безусловный, API «пропустить кадр» у sokol_app нет. После свапа
   back buffer не определён → перед следующим свапом надо обязательно
   что-то нарисовать → отсюда ре-эмнит команд в `on_frame`
   (это не костыль, а следствие модели sokol_app).

## Идея патча

Раз `sokol_app.h` уже vendored — пропатчить цикл: **не звать
`_sapp_linux_frame` вовсе, когда событий нет и перерисовка не
запрошена.** Не будет свапа — не нужен и ре-эмнит. Композитор (а на
X11 и фронт-буфер) держит последнюю предъявленную картинку.

### Шаг 1. Флаг грязности из Crystal в C

Шим (`backend/sokol_shim.c`) получает функцию:

```c
void egui_cr_set_idle(bool idle);   // вызывается из Crystal каждый кадр
```

`idle = true`, когда: событий нет (`@@events.empty?`),
`!app.ctx.needs_repaint?`, размеры не менялись, диалоги ничего не
доставили — те же условия, что сейчас в idle-ветке `on_frame`
(`sokol.cr:428-430`).

### Шаг 2. Блокирующийся цикл вместо vsync-такта

В X11-ветке `_sapp_linux_run` (только под `#if defined(_SAPP_X11)`,
Linux/GLX — первый этап):

```c
while (!_sapp.quit_ordered) {
    if (XPending(display) == 0 && g_idle) {
        // блокируемся до следующего X-события
        int fd = XConnectionNumber(display);
        poll(&(struct pollfd){ .fd = fd, .events = POLLIN }, 1, -1);
        continue;   // разбудили → разберём события обычным путём
    }
    /* существующий код: XPending / process events / _sapp_linux_frame() */
}
```

Пока есть хоть что-то живое (анимация, kinetic scroll, outstanding
repaint — `g_idle == false`) — поведение ровно как сейчас. Изменение
только для случая «спать можно долго».

### Шаг 3. Crystal-сторона

В `Backend::Sokol.on_frame` после вычисления idle-условий позвать
`LibEguiCr.egui_cr_set_idle(idle?)`. Ре-эмнит оставить как fallback
(например, для платформ, где патч не применён: win32/cocoa/EGL идут
старым путём).

## Порядок и объём

1. Шим: `egui_cr_set_idle` + глобальный флаг (~10 строк C).
2. `sokol_app.h`: блокировка в `poll()` при `XPending()==0 && idle`
   (~15 строк, одна функция).
3. `sokol.cr`: выставить флаг из `on_frame` (~5 строк).
4. Пересборка: `rake` (vendor C собирается в `libegui_cr_sokol.a`).

## Граничные случаи

- **Анимации/kinetic scroll**: они сами зовут `ctx.request_repaint`
  каждый кадр, пока живы (`context.cr:196`, `history.cr:135`) →
  `idle` остаётся false, цикл не засыпает. Отдельный deadline-таймер
  (будить не сразу, а к моменту следующего кадра анимации) — этап 2,
  не обязателен для первого результата.
- **Resize/фокус/курсор/drag&drop** — всё приходит как X-события,
  `poll()` просыпается, цикл идёт обычным путём.
- **AsyncDialogs** (`SystemPorts::AsyncDialogs.pump`): fiber-механика
  живёт на стороне Crystal и качает кадры через события/repaint;
  проверить, что завершённый диалог будит цикл (при необходимости —
  писать байт в pipe, добавленный в pollfd; отметить как риск).
- **X11 без композитора**: пропущенный свап безопасен — фронт-буфер
  двойной буферизации остаётся нетронутым.
- **Статистика `sapp_frame_count`/`sapp_frame_duration`** перестаёт
  тикать в спячке — не использовать их для логики.

## Приёмка

- `bin/hello` idle: < 0.3% ядра, пробуждений < 5/с (замер
  `/proc/<pid>/stat` полей 14+15 и `/proc/<pid>/status` voluntary).
- `bin/widgets_gallery` idle (вкладка без анимации): то же.
- Вкладка Plot (анимация CPU): плавно течёт, т.е. анимация не даёт
  уснуть; после ухода с вкладки — снова 0%.
- Ввод, resize, drag&drop, диалоги, смена темы — работают как раньше.

## Чего этот патч НЕ делает

- Не трогает win32/cocoa/EGL(Wayland) циклы (там свои run-loop'ы;
  при желании повторить приём позже).
- Не меняет ядро фреймворка: `Context#needs_repaint?` уже существует.
- Не отменяет on-demand repaint в Crystal — лишь добавляет «спячку»
  уровнем ниже.
